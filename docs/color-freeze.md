# 色彩配置冻结粒度选型分析

面向“棱版未来接入色彩配置”的选型分析。本文不假设仓库已具备 ICC、设备链接或任何外部色彩管理能力；所有结论只建立在当前仓库的实际算术、持久化结构与一个可运行的数值对照工具之上。

配套工具与复现命令：

```sh
go run ./tools/colorfreeze          # 文本报告
go run ./tools/colorfreeze -json    # 机器可读报告
```

工具中的 `paintmodel` 是 `internal/paint` 的逐行移植，只把传递函数常量参数化为命名配置；报告第一节会把移植管线与生产 `internal/raster` 做逐像素比对，当前结果为 0 个不一致像素，因此下文数值可视为生产管线在假设配置下的重放，而非另起炉灶的模拟。

## 1. 问题重述与候选冻结粒度

配置更新有利于设备一致性，但同一稿本在换机器（即换配置）后重渲染可能变色；为每个稿本复制全部转换结果又会放大保存与复用成本。候选粒度按管线位置分为三级：

| 级别 | 冻结对象 | 对应仓库位置 | 可编辑 SVG |
|---|---|---|---|
| L0 | 输入颜色（0..1 直通 sRGB 文档色） | 现有 `scene.Document` / 修订 JSON，本就是不可变事实 | 是 |
| L1 | 转换后的材料（线性光、预乘透明度的中间像素/层网格） | 当前无此持久化形态，需新增 | 否 |
| L2 | 最终像素（量化后的 NRGBA8/PNG 字节） | 现有 `Artifact`，已按内容摘要持久化 | 否 |

## 2. 当前管线审计（sRGB 输入 → 线性预乘插值 → 输出量化）

### 2.1 输入侧

- `scene.Color` 为 0..1 的浮点四元组；`validate.Unit` 限定闭区间 `[0,1]` 且拒绝 NaN/Inf（`internal/validate/validate.go:15-17`）。没有任何配置版本、色域标签或 ICC 字段，文档契约隐含“输入即 sRGB 编码值”。
- 修订不可变，稿本摘要 `SceneHash` 直接对 `scene.Document` 做 JSON 规范化后取 SHA-256（`internal/repository/repository.go:63`）。输入颜色今天已经天然具备 L0 冻结，无需新增存储。

### 2.2 解码与预乘

- `paint.linear` 是 IEC 61966-2-1 分段传递函数：`v<=0.04045 → v/12.92`，否则 `((v+0.055)/1.055)^2.4`（`internal/paint/paint.go:12-17`）。
- `paint.From` 先逐通道解码，再乘 alpha 完成预乘；alpha 本身不经传递函数（`paint.go:25-27`）。组透明度在整层合成之后才施加（`raster.go:42` 的 `src.Scale(l.Layer.Opacity)`），符合规范“组透明度在整层合成后施加”。

### 2.3 插值与混合

- 渐变在**线性、预乘**像素空间做线性插值，且 alpha 通道同样在预乘空间插值（`paint.go:43-49`）。这正是与多数 SVG 查看器（sRGB 空间插 stop）的分歧点，`vector.go:31-32` 已明确不承诺逐像素相同。
- `paint.Over` 的非 normal 分支先除以各自 alpha 还原直线色，做 multiply/screen，再按 Porter-Duff 权重重组并重新预乘（`paint.go:53-66`）。`src.A==0 || dst.A==0` 时退化为普通 over，避免除零。
- 覆盖采样为每像素 2×2 四点，在**线性预乘空间**平均（`raster.go:24-48`），画布上限 512×512。

### 2.4 量化边界

- `paint.RGBA8`（`paint.go:29-34`）的实际边界行为，经工具逐码验证：
  - `A<=0` 一律输出 `(0,0,0,0)`，RGB 载荷被丢弃——完全透明像素不携带颜色信息，L2 冻结无法保留“透明但有色”的意图；
  - 编码前对线性值 clamp 到 `[0,1]`，再 `math.Round(x*255)`（半数远离零），因此输出永远落在 0..255，不可能产生 256；
  - 对 k=0..255 全部输入码做“编码→解码→重编码”往返，三种候选配置下最大误差均为 0、可达码均为 256/256，量化是满射且无码洞；
  - 探针值：生产配置下输入 0.5 → 128、0.04045 → 10、0.0031308 → 1、1.0 → 255。
- 实测 HTTP 渲染产物：不透明画布输出 color type 2（RGB），半透明文档输出 color type 6（RGBA）；PNG 内只有 `IHDR/IDAT/IEND`，**没有 gAMA、cHRM、iCCP 等任何色彩块**。即 PNG 字节本身不携带配置声明，色彩解释完全依赖外部约定，这是未来兼容设计必须正视的缺口。
- 半透明实测（4×4、alpha=0.5 实色）：输出 `NRGBA=(153,76,26,128)`，alpha 为 `round(0.5*255)=128`，与算术一致；边缘像素因四点覆盖不同而不同，属预期。

### 2.5 身份与持久化事实

- 成品键 = `Hash(plate:revision:scene_digest:format:content_digest)`（`service.go:136`）。同稿本重渲染得到相同成品（实测两次 render 返回同一 id）；只要配置变化引起字节变化，内容摘要变化会自然生成**新**成品，旧成品与已 accepted 校样继续受“不可撤销/不可悄悄替换”规则保护。
- 但成品元数据里没有配置版本字段；封包 `prism-plate-bundle-v1` 只含稿本历史，不含成品（`bundle.go:13-25`）。因此今天把封包拿到另一台机器，重渲染结果只对“同一编译算术 + 同一隐含 sRGB 约定”有保证，配置一旦可配，跨机重放没有任何显式依据可校验。

## 3. 数值对照设计

工具构造两个场景，均为可运行的真实管线重放：

1. `transparent-gradient`：64×48，深色不透明背景上覆盖对角线性渐变，stop 为 `(1,0.7,0.22,a=1) → (0.9,0.18,0.14,a=0.25)`，同时跨越色相与透明度；
2. `gradient-plus-screen-glaze`：在场景 1 上叠加 opacity=0.72 的 screen 青色实色层，走 `Over` 的非预乘/再预乘分支。

三个配置（均为纯算术、无 ICC）：

- `srgb-iec 1.0.0`：当前生产常量（参照世界）；
- `gamma-2.2 1.1.0`：替换为纯 2.2 幂律，代表设备一致性升级中最典型的传递函数更换；
- `wide-knee 1.2.0`：保留 2.4 幂律但把线性段放宽到 0.06，代表厂商暗部微调。

对照口径：以 `srgb-iec` 的输出为基准，重放每个配置，统计全画布最大每通道字节差（0..255）与线性预乘空间最大差（0..1）。

## 4. 实测结果（工具报告摘要）

### 4.1 三级冻结在配置更换下的稳定性

透明渐变场景（混合背景场景结论同构，数字见报告）：

| 冻结级别 | 重放配置 | 最大 dR/dG/dB/dA（字节） | 线性颜色最大差 | 线性 alpha 最大差 |
|---|---|---|---|---|
| L0 输入颜色 | gamma-2.2 | **2 / 2 / 1 / 0** | 0.008176 | 0 |
| L0 输入颜色 | wide-knee | 1 / 1 / 0 / 0 | 0.000176 | 0 |
| L1 线性材料 | gamma-2.2 | 2 / **6 / 6** / 0 | 0 | 0 |
| L1 线性材料 | wide-knee | 0 / 0 / 0 / 0 | 0 | 0 |
| L2 最终像素 | 任意配置 | **0 / 0 / 0 / 0** | 0 | 0 |

三个关键事实：

1. **L0 的漂移是真实但有界的**：传递函数更换会让同稿本 PNG 出现最多 2 个码值的变化（本场景规模下），PNG 摘要随之改变；alpha 通道不经过传递函数，dA 恒为 0。
2. **L1 不能承诺跨机逐像素一致**：线性材料冻结后，线性空间差确实归零，但目标机仍要用自己的传递函数重新编码，gamma-2.2 下出现最多 6 个码值的变化，反而比 L0 的字节差更大。L1 只冻结了“光”，没有冻结“码”。对 wide-knee 这类只改暗部线性段的配置，L1 在本场景恰好无差，但这是配置形态的巧合，不能写进保证。
3. **只有 L2 能把字节差钉死为 0**，与配置无关；PNG 摘要表显示 L2 在三台“机器”上摘要前缀完全相同，而 L0/L1 各自产生新摘要。

### 4.2 透明渐变的插值空间风险（与冻结正交，但影响 SVG 承诺）

渐变中点像素，生产管线（线性预乘插值）与朴素 sRGB 编码空间插值对照：

| 方法 | 中点 NRGBA（生产配置） | 线性 G 通道 |
|---|---|---|
| canonical-linear-premult | (202,131,44,255) | 0.225215 |
| naive-sRGB-mix | (196,89,39,255) | 0.100062 |

同一输入、同一配置，仅插值空间不同，G 通道就相差 42 个码值，远大于任何传递函数更换造成的漂移。这量化了现有 README“SVG 不承诺逐像素相同”的代价区间，也说明：**任何冻结方案都无法让可编辑 SVG 获得 PNG 级承诺**，因为分歧发生在查看器内部，不受本服务控制。`color-interpolation="linearRGB"` 只是提示，查看器支持度不一。

### 4.3 保存与复用成本

| 形态 | 64×48 单层实测 | 512×512 单层外推 | 可恢复几何/笔刷/SVG |
|---|---|---|---|
| L0 稿本 JSON | 328 B（双层场景 471 B；真实 amber 稿 6 293 B） | 与像素尺寸无关，只与结构有关 | 是 |
| L1 float64 线性预乘网格（每层） | 98 304 B | 8 388 608 B（8 MiB） | 否 |
| L2 原始 NRGBA 网格 | 12 288 B | 1 048 576 B（1 MiB） | 否 |
| L2 PNG（实际编码后） | 521 B / 447 B | 典型远小于原始网格 | 否 |

L1 单层 512² 网格就是 8 MiB 浮点，是同尺寸 L2 原始网格的 8 倍、PNG 字节的数十倍；而且 L1 是拍平结果，几何、笔刷、混合模式、SVG 可编辑性全部不可恢复，等于为一个“仍不保证逐像素一致”的中间态付出最贵的存储。当前快照上限 128 MiB、成品上限 256 条，引入 L1 持久化会立刻与容量预算冲突。

## 5. 三种粒度能承诺什么

| 承诺项 | L0 输入颜色 | L1 线性材料 | L2 最终像素 |
|---|---|---|---|
| 同机同配置重渲染逐像素一致 | 是（现有不变量，实测同 id） | 是 | 是（字节即事实） |
| 跨配置/跨机 PNG 字节一致 | 否，差异有界且摘要变化（实测最多 2 码值） | **否**，重编码可产生更大差异（实测最多 6 码值） | **是，恒为 0 差异** |
| 保留可编辑 SVG 与几何复用 | 是 | 否 | 否 |
| 透明像素的颜色意图 | 保留在文档里 | 受拍平影响，`A<=0` 处 RGB 被清零 | 丢失（PNG 里为 0,0,0,0） |
| 存储增量 | 零（现状即如此） | 最大（8 MiB/层@512²，不可压缩复用结构） | 小且已有（PNG 实测数百到数千字节） |
| 与现有成品/校样生命周期兼容 | 需补配置版本元数据 | 需新增实体、校验与容量规划 | 天然兼容，只需补配置来源声明 |
| 对“配置更新促进设备一致”的支持 | 新配置只影响新渲染，旧事实不动 | 同 L0，且收益不完整 | 新配置产出新 L2 成品，旧校样冻结在旧字节 |

## 6. 选型建议：L0 为事实源 + L2 为跨机承诺，L1 不入库

**推荐组合：以 L0 为唯一权威输入并保持不可变，以 L2（PNG 成品字节）作为跨机器、跨配置的唯一逐像素承诺；不把 L1 作为持久化冻结边界。**

理由全部由上节数值支撑：

1. L0 已被修订不可变与稿本摘要覆盖，零新增存储，且是唯一能继续产出可编辑 SVG 的形态；设备一致性升级通过“新配置渲染新成品”获得，不篡改旧稿本，符合“旧稿本不可改写”的主不变量。
2. 跨机换机器后“旧校样不变色”的诉求，只有 L2 能严格兑现（dR/dG/dB/dA 恒为 0）。而 L2 正是系统今天已经在做的事——成品按内容摘要存储、accepted 校样禁止撤销。需要补的不是新存储，而是**让 L2 字节携带可验证的配置来源**（见第 7 节），以及在封包场景允许按需附带成品。
3. L1 在本仓库的成本收益最差：8 MiB/层的浮点网格、不可逆地丢失可编辑性、却仍挡不住重编码漂移（6 码值实测）。它唯一合理的位置是**进程内渲染缓存**（同一配置下避免重复解码/插值），随进程消亡，不进入 `state.json`、不进封包、不参与谱系校验。这样复用性能与持久化成本解耦。
4. 对“每个稿本复制全部转换结果成本高”的回应：不需要全量复制。L0 稿本本来就是共享事实；L2 只对**需要跨机承诺的成品**（尤其是已开/已通过的校样）保留，且 PNG 压缩后体积很小。封包继续默认只装稿本；需要移交视觉承诺时再显式附加对应成品字节与配置声明，由导入侧决定信任与否，而不是隐式重渲染冒充一致。

SVG 的定位维持现状并写入承诺边界：SVG 是 L0 的矢量派生物，受查看器插值空间影响（实测单点 42 码值量级），任何配置版本都不对 SVG 做逐像素承诺；需要逐像素交付时以 L2 PNG 为准。

## 7. 版本与兼容边界（不含 ICC 的落地约束）

建议的版本化对象与规则，均为现有结构的增量，不引入外部色彩管理依赖：

1. **配置是命名、带版本的纯算术常量集**，最小字段即工具中 `Config` 的形状：`name/version` 加传递函数常量（thresh、linearDiv、offset、scale、gamma），外加插值空间与混合模式枚举（当前固定线性预乘 + normal/multiply/screen）。禁止把“配置”做成可执行代码或外部文件引用。
2. **渲染事实记录 `color_config` 名与版本**。在 `Artifact` 增加配置标识字段，并把它纳入成品键输入（与 `service.go:136` 的现有键拼接并列），使同稿本不同配置天然生成不同成品、同一事实永不被覆盖；`repository.Check` 的谱系校验增加该字段非空且属于已知配置集的检查。旧快照无该字段时按 `srgb-iec@1.0.0` 隐式补齐——这正是当前唯一存在过的算术，兼容等价。
3. **schema 分版而非就地改写**：`prism-plate-v1` 快照与 `prism-plate-bundle-v1` 封包保持原样只读；需要配置字段时出 `v2`，`Open`/`Check` 对未知 schema 继续硬拒绝（沿用 `repository.go:97` 的现有行为）。v1 数据在 v2 进程里走一次性、可审计的默认配置升级，升级失败不得成为内存事实（沿用现有提交点语义）。
4. **配置弃用规则**：渲染器可以新增配置，但不得删除或静默改变已发布版本的常量；修改常量必须发新版本。旧版本渲染器遇到只含已知配置的事实时必须能继续读取与校验；遇到未知配置版本，拒绝渲染并返回明确错误，不得回退到默认配置“近似渲染”。
5. **PNG 字节的声明边界**：当前 PNG 无 gAMA/iCCP/cHRM 块，保持“裸 sRGB 码值 + 外部元数据声明”的形态。配置标识放在成品元数据/封包清单里，不写进 PNG 内部，避免标准库编码器不支持带来的兼容分叉；消费方若需嵌入色彩块，属于独立能力，不在本承诺内。
6. **封包兼容**：v1 封包维持“只含稿本”语义不变；v2 封包可选附加 L2 成品段（字节 + 内容摘要 + 配置版本），导入侧逐段验摘要，附加段缺失不影响稿本导入，但必须明确告知“无成品段则不承担跨机逐像素承诺”。导入重名拒绝、不合并历史的规则不变。
7. **承诺口径写死**：L0 承诺“同配置下确定性重放 + 可编辑”；L2 承诺“字节级跨机一致，受 PNG 8-bit 量化与透明像素 RGB 清零边界约束”；任何级别都不承诺 SVG 逐像素、不承诺超出现有 512²/四点采样的视觉正确性，也不声明 ICC 级色域转换。配置体系演进到需要真正色域映射时，是另立 schema 与实体的新项目，不在本文档的兼容伞下。

## 8. 结论

- 冻结输入颜色（L0）解决“事实源可编辑、可追溯、零存储增量”，但单独存在时跨机变色有界却真实（实测 ≤2 码值）。
- 冻结转换材料（L1）在本仓库是错误的持久化边界：挡不住输出重编码（实测可达 6 码值差异）、体积 8 倍于 L2、且摧毁可编辑性；只适合做进程内缓存。
- 冻结最终像素（L2）是唯一能把跨机差异承诺为 0 的粒度，且系统已具备其存储与生命周期骨架，缺的只是配置来源的显式版本化与封包可选携带。
- 推荐落地路径：保持 L0 不可变 → 为成品与渲染请求引入 `color_config@version` 并纳入成品键与谱系校验 → schema v2 承载新字段、v1 按 `srgb-iec@1.0.0` 等价升级 → 封包 v2 可选附带 L2 字节 → L1 仅作进程内缓存。全部基于现有标准库与算术，不依赖 ICC。
